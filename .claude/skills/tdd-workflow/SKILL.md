# TDD Workflow

## 目的

実装前に期待する振る舞いをテスト可能な形にし、実装後にその振る舞いと既存機能への影響を確認する。TDDは品質を考えるためのループであり、固定された儀式や特定モデルの呼び出しではない。

## 適用条件

- 外部から観測できる振る舞い、バグ修正、データ変換、状態遷移、認証・権限境界を変更するときに使う。
- 文書だけの変更や、テストで検証できない調査では、必要な確認方法を別に選ぶ。
- 受入条件が曖昧なら、実装前に期待する入力・出力・失敗条件を明確にする。

## 進め方

1. 受入条件から、正常系・失敗系・境界条件・権限境界のうち今回の変更に関係するシナリオを選ぶ。件数はリスクと既存テストの状態で決める。
2. 新しい振る舞いなら、実装がない状態で失敗するテストを置く。既存の不具合なら、現在の不正な振る舞いを再現するテストを先に置いてもよい。
3. 受入条件を満たす最小の実装を行い、選んだテストを通す。仮実装、三角測量、先に全シナリオを書くことは必要な場合だけ使う。
4. 変更に直接影響するテストを再実行し、必要に応じて関連テスト・統合テスト・全体検証へ広げる。実行範囲と理由を記録する。
5. テストが通った状態を保ちながら重複や境界を整理する。検証結果が変わった場合は原因を確認してから完了とする。

Red-Green-Refactorは有効な進め方だが、既存テストの補強、設定変更、移行作業などでは適用できる部分だけを使う。固定の工程順、特定のエージェント、モデル、リトライ回数を完了条件にしない。

## 成果と検証

- 受入条件に対応するテストまたは別の検証方法が特定されている。
- 失敗・成功の結果、実行したコマンド、未確認の範囲を残す。
- テストが通ることだけで、本番・外部サービス・認証境界の成立を断定しない。必要なら実際の境界を通る統合検証やreadbackを追加する。
- 例: `npm run test:run -- <affected-test-file>`。リポジトリの既存コマンドと対象範囲を優先する。

## 注意

テストが存在することや件数が多いことは、受入条件を満たす証拠ではない。入力不足、テスト未実行、外部依存の失敗は成功に変換せず、未確認として報告する。
