# Daily Reflection

## 目的

利用者が寝る前に必要なのは、活動の全件報告ではない。

- 今日、何が閉じたか
- 何が閉じず、なぜ明日へ残るか
- 将来の本人判断に再利用できる学びは何か

この3点をBrainbaseの記録から確定し、未確認を隠さず短く返す。

## 責務境界

### このSkillが行うこと

- 対象日の判断結果とowner-visible監査状態を確認する
- Run Receiptの履歴から成功、部分成功、未確認、失敗を区別する
- 閉じたこと、持ち越し、Personal KG候補を整理する
- 組織事実らしい内容をPersonal KGと分け、`昇格レビュー待ち`として根拠だけを残す
- ルーティン結果をBrainbaseの実行記録へ残す

### このSkillが行わないこと

- 外部サービスの直接巡回または再収集
- SNSの生成、分析、投稿、反応取得
- カレンダー、メール、Slack、議事録、transcriptの探索
- NocoDB、Git/GitHub、Wiki、Codexタスク全件の棚卸し
- HTMLレポート、セッションarchive、memory preambleの生成
- Graph SSOTへの自動書き込み
- 外部送信、公開、削除、不可逆な変更

外部連携の事実は、Brainbaseへ正規化されたRun Receiptがある時だけ利用する。元サービスへフォールバックしない。

## 正本の分担

| 正本 | 保持するもの | このSkillでの扱い |
|---|---|---|
| Graph SSOT | 組織の正式な事実、関係、決定 | このSkillでは参照・判断しない。`/retro`だけが昇格候補を照合する |
| Personal KG | 本人の判断基準、制約、学び、個人文脈 | owner-visible候補を作る。組織事実や公開素材へ暗黙に投影しない |
| Run Receipt | 実行結果、部分取得、未確認、失敗、診断可能な履歴 | 日次状態の主な証拠。latestと履歴を混同しない |
| Judgment audit | そのturnで採用された判断経路と実際の参照 | 判断結果の由来確認。行動許可や事実証明の代わりにしない |

## 入力

必要最小限のBrainbase入力だけを取得する。

1. 対象日のRun Receipt履歴
2. 対象日に閉じた判断と、継続中の判断
3. 対象日のPersonal KG候補とレビュー状態

取得結果には、少なくとも次を保持する。

- 取得元
- 対象期間
- 取得時刻
- 状態
- 取得できた範囲
- 失敗理由または未確認理由

## 実行手順

### 1. 対象日を確定する

- 明示日付があればそのJST日付
- 対話で明示がなければ当日
- 夜間自動化で明示がなければ前日

対象日を推測した場合は、最終表示に短く明記する。

### 2. 入力の健全性を判定する

取得前に「0件」を置かない。入力ごとに次を区別する。

- `confirmed_empty`: 取得成功かつ対象なし
- `available`: 取得成功かつ対象あり
- `partial`: 一部だけ取得
- `unconfirmed`: 結果を確定できない
- `unavailable`: 接続または機能を利用できない
- `failed`: 実行失敗

認証失敗、未接続、timeout、期限超過のReceipt未着、履歴欠落は`confirmed_empty`ではない。Receipt未着とするのは、現在有効なAutomation定義が対象Runと実行予定・猶予時間を宣言し、その期限を過ぎた場合だけ。無効化・廃止済み、期待期限なし、対象Runなしの処理は入力欠落に数えない。

### 3. 今日閉じたことを決める

次の条件を満たすものだけを「閉じた」とする。

- 結果が明示されている
- 未確認の依存を成功として補完していない
- 同じ論点の新しいReceiptと矛盾しない
- テスト、commit、merge、routing receiptだけを利用者価値の成功へ読み替えていない

単なる作業ログ、重複、FYIは通常表示から除く。

### 4. 明日への持ち越しを決める

持ち越しには次のいずれかだけを入れる。

- 人間判断が必要
- 実行が部分成功、未確認、失敗
- 依存先の状態変化を待っている
- 次の具体的な確認または再試行がある

各項目へ「残る理由」と「次に必要なこと」を付ける。owner、期限、次の行動を根拠なく補完しない。

### 5. Personal KG候補を作る

候補にするのは、将来の本人判断を改善する再利用可能な内容だけ。

- 繰り返し現れた判断基準
- ユーザー訂正で明確になった好みまたは停止線
- 成否を分けた制約
- 別の場面にも適用できる学び

候補にしないもの:

- その日だけの作業一覧
- 根拠のない推測
- 組織の正式な事実や決定
- 第三者の秘密を一般化せず含む本文
- 既存候補の言い換え

provenance、sensitivity、visibilityを保持する。安全性または適用範囲が未確定なら`needs_review`にする。既存の承認済みwriterが利用できない時は、書き込み成功を装わず候補本文だけを返す。

### 6. 昇格レビュー待ちを分離する

組織の正式な事実、関係、RACI、正式な決定に該当する可能性があるものは、Personal KGへ混ぜず`昇格レビュー待ち`とする。

- 元の根拠、対象、機密性だけを保持する
- 既存Graphの検索、重複判定、正式名称の確定は行わない
- 昇格の推奨または却下を行わない
- `/retro`がまとめてGraphを照合し、`Graph候補`、`見送る`、`保留`を判断する

### 7. 実行状態と確認範囲を分ける

未解決や未確認を正しく表示できたことと、ルーティン自身の失敗を混ぜない。

| 実行状態 | 条件 |
|---|---|
| `成功` | 取得を試み、分類、表示、実行記録の保存を完了した |
| `部分成功` | 表示または実行記録は残せたが、ルーティン自身の一部処理を完了できない |
| `失敗` | 利用者が使える結果を生成できない、または実行記録を残せない |

| 確認範囲 | 条件 |
|---|---|
| `確認済み` | 必須入力を取得し、閉じたことと持ち越しを確定できた |
| `部分的` | 一部だけ取得でき、確認できない範囲と影響を示せる |
| `未確認` | 必須入力を確認できず、日次状態を確定できない |

未確認を正しく表示して実行記録を残せた場合、実行状態は`成功`でもよい。ただし確認範囲を`確認済み`へ繰り上げない。

### 8. 表示する

本文は次の順にする。

1. 実行状態と確認範囲
2. 今日閉じたこと
3. 明日へ持ち越すこと
4. 振り返り候補
5. 折りたたんだ確認根拠

内部の仕組み名、全件数、正常なFYI、長いログは本文に出さない。利用者の判断が必要な時だけ、推奨する結論、理由、影響、選択肢を1か所にまとめる。

## 失敗時の停止線

- Run Receipt履歴を取得できない: 対象日の成功を主張しない
- Personal KGが未接続: 振り返り候補を書き込まず、候補本文と未確認理由を返す
- 昇格レビュー待ちを記録できない: Personal KGへ混ぜず、候補本文と未記録理由を返す
- 実行記録を残せない: 本文を生成できても全体を成功にしない
- 部分取得: 取得できた範囲とできなかった範囲を分ける

同じ失敗を無制限に再試行しない。安全な既定の再試行回数を超えたら、原因、影響、次の確認を持ち越す。

## 関連コマンド

- `/oyasumi`: このSkillを使い、今日を閉じる
- `/ohayo`: 前夜の持ち越しと夜間状態から、今日の要判断を出す
- `/retro`: 日次履歴から繰り返す問題を仕組み変更へ変える
