# Architecture Patterns

## 目的

アーキテクチャ上の判断を、変更された境界と受入条件に結びつける。EventBus、Reactive Store、DI、Service Layerは候補であり、すべての変更に適用する規則ではない。

## 適用条件

変更対象のコード、呼び出し元、状態の所有者、データアクセス経路を確認し、関係するパターンだけを選ぶ。該当する境界がない場合は、適用しない理由を記録して先へ進む。

- **EventBus**: 独立した購読者へドメインイベントを通知する必要がある場合に使う。単一の直接呼び出しを無理にイベント化しない。
- **Reactive Store**: 複数の画面やコンポーネントで共有する状態を一元管理する場合に使う。局所的な表示状態までStoreへ移さない。
- **DI**: 差し替え、テスト、ライフサイクル管理が必要な依存に使う。純粋な値や安定した小さな関数の直接参照を一律に禁止しない。
- **Service Layer**: 複数の入口から使う業務ルールや外部連携をまとめる。UIは表示と入力に集中させ、データアクセスの置き場所は実際の構造に合わせる。

## 確認の進め方

1. 変更の目的、入力・出力、状態所有者、依存、公開境界を整理する。
2. 関係するパターンだけについて、現状の実装、代替案、採用理由を確認する。EventBus・Store・DI・Service Layerを順に必ず実行する工程は置かない。
3. 採用した設計を実装し、不要な結合、循環依存、責務の重複がないかを確認する。コンポーネントの行数だけで違反と判定しない。

## 成果と検証

- 変更した境界と、適用・不適用にしたパターン、その根拠が説明できる。
- 受入条件に関係するユニット、統合、UI、または実行時検証を選び、結果を記録する。
- 検査対象外のパターンや未生成のGraphify結果を、問題なしの証拠にしない。
- 直接呼び出し、Store外の状態更新、直接import、UIへの業務ロジック混入は、変更の境界と実際の責務を確認したうえで問題化する。

設計チェックの完了条件は、全パターンで違反を検出することではなく、変更に関係する設計判断と検証結果が残っていることである。
