# Refactoring Workflow

## 目的

既存の振る舞いを保ったまま、責務・依存関係・移行経路を整理する。リファクタリングの対象と順序は、実際に変更する境界、利用者、データ、ロールバック方法から決める。

## 適用条件

- 複数の利用者やサービスに影響する境界、公開API、データ形式、認証・権限、配備経路を変えるときは、互換性と切り戻しを先に確認する。
- 内部実装だけの整理なら、影響する呼び出し元とテストを確認して小さく進める。
- Infrastructure、Client、Serverの順序は実際の依存関係がそうなっている場合にだけ採用する。すべての変更に同じ順序を要求しない。

## 進め方

1. 変更前の外部契約、利用者、データ経路、失敗時の状態を記録する。
2. 変更を保ちやすい単位に分け、必要ならアダプター、互換層、段階的な切替を置く。不要な互換層は増やさない。
3. 各単位で、受入条件に関係するテストと実際の呼び出し経路を確認する。
4. 新しい経路が使われ、旧経路の利用者がなく、切り戻し方法が確認できた時点で旧コードを削除する。削除を同じ変更に含める必要がない場合は分ける。

## 成果と検証

- 外部振る舞い、データ契約、認証・権限境界が意図せず変わっていない。
- 変更に直接影響するテストを実行し、必要に応じて関連テスト・統合テスト・移行検証を追加する。
- このSkill独自のカバレッジ合格値は追加せず、変更したリスクと未検証の分岐を説明する。対象repoやCIで既に定められた基準は守り、成功のために弱めない。
- 実行できなかった検証、未接続の外部依存、切り戻し未確認は未確認として残す。

リファクタリングの完了条件は、固定の3フェーズ・5ステップ・カバレッジ値ではなく、受入条件と保つべき外部契約を検証できたこととする。
