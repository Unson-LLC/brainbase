# Security Patterns

## 目的

信頼できない入力がどこから入り、どの境界を越え、どこへ出るかを確認する。安全要件は弱めず、実装の方式と脅威モデルに合った対策を選ぶ。

## 最初に確認すること

- 入力源、出力先、HTML・URL・SQL・コマンドなどの解釈される文脈
- ブラウザかサーバーか、同一生成元か外部生成元か、Cookie・Bearer・API keyなどの認証方式
- 認証だけでなく、対象リソースに対する認可とテナント境界
- サーバー側で再検証される場所、通信経路、失敗時に漏れる情報

## 条件付きの安全確認

- **XSS**: 信頼できない値をHTMLへ入れるなら、出力文脈に合うエスケープまたは安全なDOM APIを使う。通常の文字列表示は `textContent` を優先し、HTMLが必要な場合だけ、許可する要素・属性を決めたサニタイズ（例: DOMPurify）を使う。`innerHTML`を使っているという事実だけで安全・危険を決めず、値の由来とサニタイズ設定を確認する。
- **CSRF**: ブラウザがCookieや自動送信資格情報で認証し、外部生成元から状態変更要求を誘発できる場合は、CSRF token、Origin検証、SameSite設定など、採用した対策がサーバーで検証されることを確認する。POST/PUT/DELETEの全件に同じトークンを機械的に要求せず、Bearer/API key、同一生成元制約、非ブラウザ経路などの実際の境界を確認する。
- **入力検証**: 信頼境界で型、必須性、長さ、範囲、形式、許可リストをドメインに合わせて検証する。検証だけで認可やインジェクション対策を代替せず、DBではパラメータ化、出力では文脈別エスケープを使う。
- **認証・認可・通信**: 誰が操作できるか、どのリソースに触れられるか、資格情報がどの経路で送られるかをサーバー側でも確認する。クライアントの表示制御やHTTPステータスだけを認可の証拠にしない。

## 判定と成果

1. 変更がまたぐ信頼境界と脅威を記録する。
2. 関係する対策と、適用しない対策があればその理由を記録する。
3. 正常系だけでなく、未認証・権限不足・不正入力・外部生成元・失敗応答の必要な経路を検証する。
4. 重大な未対策、境界を証明できない箇所、テスト未実行は、合格や安全として扱わず、未確認または要修正として報告する。

## 検証

変更に直接関係するテストと、必要なサーバー側・ブラウザ側の統合検証を実行する。XSS、CSRF、入力検証、認可のすべてを毎回同じ順で検査する必要はないが、対象外にした境界と根拠を残す。静的なパターン一致、モデルの判定、HTTP 200だけでは脆弱性がないことを証明しない。
