## 選定の順序

1. 利用者、ワークロード、データ、可用性、法令、予算の要求を定義する。
2. Google Cloudと利用者の責任分界を確認し、管理したい範囲を決める。
3. リージョン、障害分離、遅延、データ所在地を決める。
4. 実行、ネットワーク、ストレージ、データベース、分析、AIを要求別に選ぶ。
5. IAM、秘密、暗号化、監査ログ、バックアップ、復旧を横断設計する。
6. 小さな検証環境で性能、障害、運用、費用を測る。
7. Infrastructure as Code、監視、予算アラート、廃止手順を整えてから拡張する。

## サービス領域と判断軸

| 領域 | 代表的な選択肢 | 判断軸 |
|---|---|---|
| 仮想マシン | Compute Engine | OS制御、既存資産、常駐処理、運用責任 |
| コンテナ | GKE、Cloud Run | Kubernetes制御の必要性、実行時間、スケール、運用能力 |
| アプリ・関数 | App Engine、Cloud Run、Functions系 | イベント、実行単位、制約、移植性 |
| オブジェクト | Cloud Storage | アクセス頻度、保持、復旧、ライフサイクル |
| リレーショナルDB | Cloud SQL、AlloyDB、Spanner | 規模、整合性、互換性、グローバル分散 |
| NoSQL・キャッシュ | 各マネージドデータサービス | データモデル、遅延、整合性、容量変動 |
| 分析 | BigQuery、可視化サービス | 取り込み量、クエリ特性、ガバナンス、費用 |
| AI | Vertex AI等 | データ権利、評価、推論要件、モデル運用 |

表は候補を絞る入口であり、最新仕様に基づく比較の代替ではない。

## ネットワークと安全性

- VPC、サブネット、ルート、ファイアウォールの境界と所有者を図示する。
- 公開入口、ロードバランサ、DNS、CDN、NAT、外部接続を明示する。
- IAMは個人やサービス単位の最小権限とし、長期鍵を避ける。
- 本番、検証、開発をプロジェクト等で分離し、課金と障害の影響範囲を限定する。
- バックアップの存在だけでなく、復元時間と復元結果を検証する。
- ログ、メトリクス、トレース、監査証跡を障害前から収集する。

## コストと運用

- コンピュートだけでなく、保存、通信、ログ、バックアップ、API利用を見積もる。
- 自動スケールには上限を置き、予算アラートを停止機構と混同しない。
- マネージド化で減る作業と、ベンダー固有化・制約・費用を比較する。
- 開発速度、可用性、復旧性、セキュリティを含む総保有コストで判断する。
- 定期的に未使用資源、過剰性能、古いスナップショット、権限を棚卸しする。

## Brainbaseでの適用

Graphにはクラウドプロジェクト、システム、責任主体、環境、重要なアーキテクチャ判断を置く。Terraform等の構成と実際の稼働設定は所有リポジトリ・クラウドを正本とし、Graphは発見経路を担う。書籍の説明、現在の公式仕様、採用判断、デプロイ状態を別レイヤーの証拠として扱う。
