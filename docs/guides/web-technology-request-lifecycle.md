## 一往復を追う

```text
URL入力・操作
  → 名前解決
  → 接続と暗号化
  → HTTPリクエスト
  → Webサーバー／リバースプロキシ
  → アプリケーションのルーティングと処理
  → データベース・外部サービス
  → HTTPレスポンス
  → HTML/CSS/JavaScriptの解析・追加取得・描画
```

障害調査では「画面が動かない」をこの境界へ分解し、各層の入力、出力、時刻、識別子を確認する。

## 状態と責務

- HTTP自体の要求・応答と、アプリケーションのセッション状態を分ける。
- Cookie、セッション、キャッシュ、データベースのどこが正本かを明示する。
- クライアント検証は体験改善に使い、認可や整合性をサーバー側でも保証する。
- HTMLは構造、CSSは表現、JavaScriptは振る舞いという責務を意識する。
- Webサーバー、アプリケーション、データベースの接続数と障害影響を分ける。

## セキュリティの基本

- 入力を信頼せず、構文・意味・権限をサーバー側で検証する。
- 出力先の文脈に応じてエスケープし、XSSを防ぐ。
- 認証済みであることと、その操作を認可されていることを分ける。
- CSRF、セッション固定、Cookie属性、秘密管理、SQL注入を設計段階で扱う。
- TLSの有無だけで安全とせず、ログ、依存関係、エラー表示、権限を含めて確認する。

## 調査チェックリスト

1. 再現時刻、URL、操作、期待値、実際の応答を固定する。
2. ブラウザNetworkで要求、Status、Header、Body、Timingを確認する。
3. リクエストIDでプロキシ、アプリ、データストアのログを結ぶ。
4. キャッシュ、Cookie、認証状態を分離して再現する。
5. 症状ではなく、最初に契約が崩れた境界を根本原因とする。
