## 通信方式の選択

| 方式 | 向く用途 | 設計上の問い |
|---|---|---|
| Topic | センサーや状態など継続するデータ流 | 頻度、遅延、欠落、QoSをどう扱うか |
| Service | 短時間で終わる要求と応答 | 応答待ちで全体を止めないか |
| Action | 進捗・取消を伴う長時間タスク | 中断、再試行、部分完了をどう定義するか |
| Parameter | 実行時の構成値 | 単位、範囲、既定値、変更責任が明示されているか |

## 構築順序

1. 対象ディストリビューションと対応OSを決め、公式手順で環境を固定する。
2. ワークスペースとパッケージを作り、ビルド・起動・テストの最小ループを通す。
3. ノードの責務と、Topic・Service・Action・Parameterの契約を実装前に定義する。
4. PublisherとSubscriberから始め、必要な同期処理だけServiceまたはActionへ分ける。
5. Launchで構成を再現し、ログ、診断、記録・再生を有効にする。
6. TFの親子関係、座標軸、単位、時刻を契約化し、RVizで可視化する。
7. URDFで機構を表し、Gazebo等のシミュレーションから段階的に実機へ移す。

## 設計原則

- ノードは単一の変更理由を持たせ、ハードウェア依存とアルゴリズムを分ける。
- メッセージ名だけでなく、単位、座標系、時刻、欠損時の意味を定義する。
- QoSは通信がつながるかだけでなく、信頼性、履歴、期限、ネットワーク条件から選ぶ。
- Launchと設定ファイルで再現可能な構成を作り、手作業の端末操作へ依存しない。
- ログとbagを用いて、実機がなくても失敗を再生できるようにする。
- TFツリーとURDFを実装の付属物ではなく、システム契約としてレビューする。

## 段階的な検証

```text
関数・ノード単体
  → 通信契約の統合試験
  → 記録データの再生
  → RVizで座標・状態確認
  → シミュレーション
  → Hardware-in-the-loop
  → 制限環境の実機試験
```

各段階で期待値、タイムアウト、停止条件、ログの保存先を決める。シミュレーション成功を実機安全性の証明にはしない。

## レビューの問い

- Topic、Service、Actionの選択理由を説明できるか。
- ノード停止、通信断、遅延、重複、順序逆転を扱えるか。
- TFに循環、複数親、曖昧なframe名、時刻ずれがないか。
- 実機固有コードを差し替え可能な境界に閉じ込めたか。
- 対象ディストリビューションで公式文書とテスト結果を確認したか。
