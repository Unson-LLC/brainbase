## 協働ループ

```text
目的・制約・完了条件
  → 関連コードと一次資料を限定して提供
  → 小さな計画または差分を生成
  → テスト・型・静的解析・実行で検証
  → 人が意図・安全性・保守性をレビュー
  → 採用した変更と理由を記録
  → 失敗を次の文脈と評価へ戻す
```

プロンプトの技巧だけで精度を安定させようとしない。コード構造、命名、テスト、ドキュメント、ツールによるフィードバックが、AIとの共通インターフェースになる。

## タスクの切り分け

1. 変更対象、変更しない範囲、期待する振る舞いを明示する。
2. 調査、設計、実装、テスト、レビューを分け、一度に検証できる粒度へ落とす。
3. 必要なファイル、型、仕様、エラーだけを渡し、無関係な文脈を減らす。
4. 出力形式と検証コマンドを先に決める。
5. 差分を読み、根拠のないAPI、依存関係、例外処理、セキュリティ前提を確認する。
6. 検証結果を根拠に次の指示を更新し、会話上の自己申告だけで完了としない。

## AIが扱いやすいコードベース

- ファイルと関数の責務を小さくし、関心を分離する。
- 一意で検索可能な名前、明示的な型、安定したインターフェースを使う。
- スタイル、アーキテクチャ、安全境界をリポジトリ内の文書に置く。
- 単体テスト、状態遷移、決定表で期待動作を機械検証できるようにする。
- 生成対象外の秘密、個人情報、重要ロジックを境界として明示する。
- 大規模な自動変更より、小さくレビュー可能なコミットを優先する。

## チーム導入

- 自動補完、対話、エージェントを同一視せず、権限とリスクで使い分ける。
- プロンプトだけでなく、成功した入力範囲、検証、失敗パターンを共有する。
- コード所有者とメンテナーを明確にし、AI生成でも責任主体を消さない。
- 利用量や生成行数ではなく、変更リードタイム、欠陥、レビュー負荷、開発者体験を測る。
- AIなしの基準値と比較し、速さの改善と品質低下を相殺して見ない。

## レビューの問い

- AIに与えた情報は必要最小限で、利用許可があるか。
- 提案されたライブラリやAPIを一次資料で確認したか。
- テストが実装の追認ではなく、要求を検証しているか。
- 差分の意図を担当者が説明でき、AIなしでも保守できるか。
- 「生成できた」と「本番で価値を出した」を混同していないか。

## Brainbaseでの適用

Graphにはプロジェクト、所有者、重要な設計判断、再利用可能な失敗パターンを置く。コード、テスト、実行可能な規則は所有リポジトリを正本とする。AIの提案、実際の差分、検証結果、マージ、デプロイ、利用者成果を別の証跡として扱う。
