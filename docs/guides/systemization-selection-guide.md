# 仕組み化・委任フレームワーク選択ガイド

4冊は競合ではなく、異なる欠陥を扱う。

| 症状 | 最初に使う知識 | 主な問い |
|---|---|---|
| 理念や人の納得がなく制度が形骸化する | 小さな会社の仕組み化 | 仕組みの土台となるビジョン・計画・成長設計はあるか |
| 社長・スター社員がいないと仕事が止まる | ガーバー流 | 人ではなく役割・方法・基準が会社に残っているか |
| リーダーが全方法を自分で考えてボトルネックになる | WHO NOT HOW | この成果のHowを所有できるWhoは誰か |
| 火消しが繰り返され、改善が蓄積しない | WORK THE SYSTEM | どのプロセスがこの結果を生み、何を文書化・修正するか |

## 統合フロー

```text
目的・ビジョン・計画を定義する
  → 必要な役割と成果基準を定義する
  → 成果を所有できるWhoを選ぶ
  → WhoへHowの裁量を渡す
  → 実行を再現可能なプロセスとして残す
  → 指標と現場フィードバックで改善する
```

## 重要な緊張関係

- ガーバー流の「人へ依存しない」とWHO NOT HOWの「適任者を探す」は矛盾しない。Whoが方法を発明・所有しても、成果と知識を組織のシステムへ戻す。
- 標準化と裁量も二者択一ではない。目的、制約、品質基準は標準化し、実現方法は適任者へ委ねる。
- 文書化は人を管理するためではなく、判断可能性・引き継ぎ・改善可能性を高めるために行う。

## Brainbase診断順

1. 目的が不明なら、上位コンテキストを解決する。
2. ownerが不明なら、役割と結果責任を解決する。
3. ownerはいるが進まないなら、成果契約と権限を確認する。
4. 一度は成功するが再現しないなら、プロセスと証拠を残す。
5. 文書が増えても成果が出ないなら、統合・削除・再設計を行う。
