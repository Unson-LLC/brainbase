## システムを分解する

```text
利用者・端末
  → URL／DNS／ネットワーク／TLS
  → CDN・ロードバランサ・Webサーバー
  → アプリケーション／API
  → データベース・ファイル・外部サービス
  → ログ・メトリクス・アラート・バックアップ
```

各境界について、入力と出力、状態の所在、責任主体、障害時の影響を明示する。HTTP一往復の詳しい調査方法は[`web-technology-request-lifecycle.md`](./web-technology-request-lifecycle.md)を参照する。

## 選定の順序

1. 利用者、業務、公開範囲、応答時間、データ機密性を定義する。
2. Webサイト、Webアプリ、社内システムのどれとして扱うかを決める。
3. クライアント、サーバー、データストア、外部APIの責務を分ける。
4. 状態の正本と、Cookie、セッション、キャッシュの寿命を決める。
5. 想定負荷、可用性、RTO・RPO、保守能力から構成を選ぶ。
6. 認証・認可、暗号化、入力検証、監査を横断設計する。
7. 監視、バックアップ、復元試験、変更・廃止の手順まで用意する。

## 構成判断のチェックリスト

- 静的配信で足りる部分と、サーバー処理が必要な部分を分けたか。
- フロントエンド、API、データベース間の契約を記述したか。
- 単一障害点、接続数、容量上限、タイムアウトを確認したか。
- CMSやクラウド導入で減る作業と、残る運用責任を区別したか。
- WAF、IDS/IPS等を置くだけでなく、検知後の対応者を決めたか。
- バックアップの作成ではなく、必要時間内の復元を試したか。
- Web化に不向きな遅延、端末、閉域、規制要件がないか確認したか。

## Brainbaseでの適用

Graphにはシステム、所有者、利用者、依存サービス、主要インターフェース、重要な設計判断を置く。実装・設定・スキーマ・稼働状態は所有リポジトリと実環境を正本とする。書籍の一般原則、採用判断、観測された運用事実を別々に追跡する。
