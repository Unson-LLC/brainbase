## 状態から設計する

| 種類 | 置き場所の原則 | 例 |
|---|---|---|
| 表示中だけの状態 | 必要とする最小のコンポーネント | 開閉、入力途中、選択 |
| 複数部品の共有状態 | 最も近い共通の所有者 | フィルター、選択中ID |
| URLで共有すべき状態 | ルーター | 検索条件、ページ、対象ID |
| サーバー由来の状態 | データ取得層とキャッシュ | 一覧、詳細、権限 |
| 永続化する業務データ | バックエンド／データベース | 顧客、注文、投稿 |

同じ事実を複数のstateへ複製せず、導出できる値は描画時に計算する。状態を持ち上げる場合も、更新権限とイベントの流れを一方向に保つ。

## コンポーネントの責務

- Propsは親から子への契約として、意味と型を狭くする。
- 表示部品と、取得・更新・認可を担う境界を分ける。
- 入力フォームは値、検証、送信中、サーバーエラーを区別する。
- Effectは外部システムとの同期に使い、通常の値計算やクリック処理を移さない。
- Custom Hookは状態を隠すためではなく、再利用する振る舞いと契約を表す。
- Contextは広域に必要で更新頻度を理解できる値に限定する。

## Next.jsで先に決める境界

1. どのルートを静的、動的、クライアント操作中心にするか。
2. データをどの実行環境で取得し、誰の認証情報を使うか。
3. URLパラメータ、キャッシュ、再検証、エラーの意味をどうするか。
4. API境界で入力検証、認証、認可、監査をどこまで担うか。
5. ブラウザへ渡してよいデータと秘密を分離できているか。

## 完了チェック

- キーボード操作、ラベル、フォーカス、読み上げ順を確認した。
- 空、読込中、失敗、権限なし、再試行の各状態を設計した。
- 重要操作をユニット／統合テストし、主要動線をブラウザで確認した。
- 不要な再描画より先に、実測した遅延、通信量、画像、バンドルを改善した。
- フレームワークの現行仕様と、原本由来の概念を混同していない。

## Brainbaseでの適用

Graphにはプロダクト、画面、利用者、所有者、主要なデータ境界と設計判断を置く。コンポーネント、ルート、型、テスト、依存バージョンは所有リポジトリを正本とする。本ガイドは長期利用しやすい設計原則であり、現在の実装状態やデプロイ済み機能の証拠ではない。
