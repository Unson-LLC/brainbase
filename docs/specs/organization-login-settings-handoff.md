## 目的と実装先

組織の管理者が設定画面でログイン方法を選び、保存後にその組織のメンバーのログインへ反映できるようにする。
基盤は UNS-90 の組織別ログイン方法制御を再利用する。Slack / Google / WorkOS などの候補は例であり、実際に設定可能な方法は基盤が対応し、利用できるものに限る。

この画面は組織、メンバー、管理者権限を必要とするため、[採用済みの所有境界](../architecture/oss-organization-ui-ownership.md)に従い `Unson-LLC/brainbase-organization` が所有する。
本 OSS に組織管理画面、認証ポリシー保存層、組織向けログイン導線を追加しない。
顧客設定 repo はテナント固有の接続値と既定値を供給する。製品の画面と API は顧客設定 repo にコピーしない。

## 組織版で具体化する契約

以下は実装時に確認する要件であり、利用可能な API の宣言ではない。エンドポイント名、保存形式、環境変数との優先順位は組織版の仕様とテストで確定する。

- 認証済みの組織と管理権限をサーバーで検証する。クライアントが渡す組織 ID や非表示ボタンだけを認可の根拠にしない。
- 取得結果は保存された設定、実効的なログイン方法、設定元、利用可能な候補を区別する。未設定、取得失敗、権限不足を同じ空の選択肢へ変換しない。
- 保存時は候補と設定可能性をサーバーで再検証する。空の選択や利用不能な方法だけの選択により、全員がログインできなくなる変更を拒否する。
- 組織切り替え後に古い取得・保存応答を別組織の設定として表示しない。同時編集による上書きも検出し、再取得を案内する。
- 保存成功後は正本 API から読み直す。送信した選択値をそのまま成功表示に使わず、実効設定を表示する。保存後の再取得が失敗した場合は、反映確認が未完了であることを示す。
- ログイン画面の候補表示と実際のログイン開始・コールバック・MCP OAuth の認可に同じ実効ポリシーを適用する。画面から隠した方法でも URL の直接指定で迂回できないようにする。
- UNS-90 の staging 限定・既定 off を維持する。設定 UI の追加を機能の本番有効化や新しい認証資格情報の登録と混同しない。

## 受け入れ確認

| 操作・条件 | 確認する結果 |
| --- | --- |
| 管理者が保存し、画面を開き直す | 保存値と実効値が正本の読み直し結果と一致する |
| 一般メンバーまたは別組織から取得・更新する | サーバーが拒否し、設定も認証動作も変わらない |
| 未対応・利用不能・空の方法を送る | 保存を拒否し、以前の有効な設定を保つ |
| 取得・保存・保存後の読み直しが失敗する | 各失敗を表示し、成功や未設定と取り違えない |
| 組織切り替え中に古い応答が到着する | 切り替え先に古い組織の値を表示・適用しない |
| 同時編集が競合する | 上書きを拒否し、最新の設定を再取得できる |
| 無効化された方法を直接指定する | ログイン開始・認証完了の双方で拒否する |
| 機能フラグが off | UNS-90 の既存のログイン動作を維持する |

組織版の PR には desktop/mobile の変更前後のスクリーンショットと、認可・保存・ログイン反映のテスト結果を付ける。
この文書の追加だけでは設定画面も保存 API も提供されない。UNS-346 の機能完了判定は UNS-345 の実装と検証に依存する。
