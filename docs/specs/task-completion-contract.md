# Taskのゴールと完了条件

状態: 実装中。未リリース。条件ごとの証拠審査・稼働環境への反映は未実装。

## 問題と今回の範囲

Taskの説明文と成果物参照だけでは、「利用者が求めた成果のどの条件が満たされたか」を照合できない。作業やテストの成功を、そのままゴール達成として扱う余地がある。

Canonical Taskに任意の `completion_contract` を持たせる。Taskの正本・version/CAS・監査を再利用し、別のタスク管理を作らない。

```json
{
  "goal": "利用者が確認できる最終成果",
  "criteria": [
    { "id": "criterion-1", "condition": "何を確認できれば満たされたと言えるか" }
  ]
}
```

既存Taskの未設定状態を許容する。設定する場合は空のゴール、空の条件、重複した条件ID、未知の項目、不正な型、過大な入力を拒否する。作成・取得・更新・一覧の経路で内容を保持し、更新には既存CASを適用する。

ゴールと条件本文は各2,000文字以内、条件は1〜50件。条件IDは表示名ではなく機械参照用とし、1〜64文字のASCII英数字・`.`・`_`・`-`を許容する。先頭は英数字に限る。日本語の説明は条件本文へ記載する。未設定や明示的なnullは契約なしを表す。契約の解除・変更権限と旧提出の失効は後続のホスト側で制御する。

このフィールドに `satisfied` や自己認定の証拠配列を加えない。条件の保存は、条件達成の証明ではない。

## 後続の完了ゲートに必要なもの

このAPI追加だけでは、完了遷移の保護は完成しない。ホスト側で以下を揃えるまで、成果に基づく完了制御を導入済みとは報告しない。

1. 保存用DB移行とadapterの読み書き。Task本体が唯一の正本であること。
2. submissionに条件IDと証拠参照の対応を保存する。対象のTask contractの版またはdigestを固定する。
3. 全条件の対応が存在し、証拠参照を取得・照合できることを確認する。参照文字列があるだけでは合格にしない。
4. 人間受入で最新submissionと現行contractを審査する。contract変更後は旧版への受入を流用しない。条件の削除・緩和で審査を迂回できないよう、変更権限も検査する。
5. generic completionとhuman completionの双方で同じ条件を確認する。対象条件が未充足ならTaskを未完了のまま保持する。

Organizationの委任・審査・認証は拡張側の責務とし、公開kernelへ内部運用・顧客値を持ち込まない。公開kernelは共通のデータ契約を提供する。

## 検証

- 既存Taskの読み書きが維持される。
- 設定したゴール・条件ID・条件本文が保存後も一致する。
- 不正な型・空条件・重複ID・未知項目・過大入力を作成と更新で拒否する。
- 古いversionでcontractを上書きできない。
- 完了条件を保存できたことを、証拠審査や実運用の効果と混同しない。

残る別範囲: HostのTask必須結合、証拠差分による停滞検出、時間/token/費用予算、質問・方針変更への切替、実際の判断改善と本人評価。
