## エグゼクティブサマリー

本書の法則は、完成した画面へ後付けするチェック項目ではない。ユーザーが何を期待し、何を認識し、どこで迷い、どの瞬間を記憶するかを、設計前から考えるための仮説群である。

実務では次の順で使う。

1. ユーザーの目的と利用文脈を確認する。
2. 目的達成を妨げる認知負荷、操作負荷、待ち時間、感情的なピークを特定する。
3. 関連する心理学的原則を「説明」ではなく設計仮説へ変換する。
4. 原則をチーム固有の短いデザイン原則と、検証可能なルールへ落とす。
5. ユーザー調査、行動観察、ユーザビリティテスト、定量データで検証する。
6. 事業KPIだけでなく、ユーザーの自律性、時間、注意、ウェルビーイングへの影響を確認する。

重要なのは、法則を絶対視しないことだ。法則はユーザーリサーチの代替ではなく、観察すべき点と検証仮説を作るための補助線である。

## 10の法則

### 1. ヤコブの法則 — 慣れを出発点にする

**意味**: ユーザーは他の製品で得た経験を、新しい製品にも持ち込む。一般的なパターンに沿えば、操作方法の学習ではなく本来のタスクへ集中できる。

**設計への変換**:

- ナビゲーション、検索、フォーム、決済などは、まず標準パターンから設計する。
- 大きな変更では旧版との移行期間、説明、段階的な導入を用意する。
- 独自UIは「新しいから」ではなく、ユーザーの主要目的を明確に改善できる場合だけ採用する。
- 慣例から外れる場合は、理解可能性をユーザーテストで確かめる。

**誤用**: すべてを競合と同じにすることではない。差別化より先に、差別化が学習コストを上回る価値を持つかを問う。

**検証質問**: 初見のユーザーは、過去の経験から次の操作を予測できるか。

### 2. フィッツの法則 — 重要な操作を大きく、近く、押しやすくする

**意味**: 対象へ到達する時間と誤操作率は、対象の大きさ、距離、入力方法に左右される。

**設計への変換**:

- 主要操作には十分なターゲットサイズと周囲の間隔を与える。
- 頻繁な操作を親指、ポインタ、視線などが到達しやすい位置へ置く。
- 破壊的操作は誤タップしやすい場所から離す。
- マウスだけでなく、指、キーボード、支援技術、空間入力を考慮する。
- 実際の利用環境を観察するコンテクスチュアル・インクワイアリーを使う。

**誤用**: 重要でない操作まで大きくすると視覚階層が壊れる。大きさは重要度と利用頻度を反映させる。

**検証質問**: 移動中、片手、視力・運動能力に幅がある状態でも操作できるか。

### 3. ミラーの法則 — 数を7個に制限せず、意味でチャンク化する

**意味**: ワーキングメモリには限界があるが、固定的な「7±2」をUI項目数の上限として使うのは誤り。重要なのは情報を意味のあるまとまりへ整理することだ。

**設計への変換**:

- 長い番号、フォーム、説明、一覧を意味のある単位へ分割する。
- 見出し、余白、グループ名、順序によって構造を外在化する。
- ユーザーに記憶させず、必要な情報を必要な場所で見せる。
- 初心者と熟練者ではチャンクの意味が異なることを考慮する。

**誤用**: 常時見えているメニューを機械的に7件以下へ削ること。記憶負荷と視認可能な選択肢を混同しない。

**検証質問**: ユーザーは情報を覚えたまま画面間を往復させられていないか。

### 4. ヒックの法則 — 選択を減らすだけでなく、判断の文脈を明確にする

**意味**: 選択肢の数と複雑さが増えるほど、意思決定に時間がかかる。

**設計への変換**:

- 主要目的に関係しない選択肢を削るか後段へ送る。
- 選択肢を分類し、推奨、既定値、比較軸を明らかにする。
- 複雑なフローを段階化し、一度に判断する範囲を小さくする。
- 抽象的なアイコンにはテキストラベルを付ける。
- 単純化で情報の意味や発見可能性を失わないようにする。

**誤用**: UIを隠せば単純になると考えること。発見不能な機能や曖昧なアイコンは、むしろ判断コストを増やす。

**検証質問**: 各画面でユーザーが答えるべき問いは一つに絞られているか。

### 5. ポステルの法則 — 入力には寛容、出力には厳密

**意味**: 人間の多様で不完全な入力を受け入れ、システム内部では一貫した形式へ正規化する。

**設計への変換**:

- 電話番号、日付、空白、表記揺れなどを可能な範囲で自動解釈する。
- 入力形式を強制する前に、不要な項目自体をなくす。
- 多言語、長い文字列、右から左の表記、文字拡大に耐えるレイアウトにする。
- 正常系だけでなく、異常系、極端値、支援技術を含む入力を試す。
- 正規化結果をユーザーが確認・修正できるようにする。

**誤用**: 何でも黙って受理すること。曖昧な推測が重大な結果を生む場合は確認を挟む。

**検証質問**: システム都合の形式変換をユーザーへ手作業で押し付けていないか。

### 6. ピークエンドの法則 — 体験の感情的な山場と終わりを設計する

**意味**: 人は体験全体の平均より、感情が最も動いた瞬間と終了時の印象を強く記憶する。

**設計への変換**:

- ジャーニーマップでポジティブ／ネガティブなピークを特定する。
- 登録、決済、失敗、解約、サポートなど感情が動く場面を優先改善する。
- リアルタイムバリデーションなどで失敗前にガイドする。
- 完了時には結果、次の行動、安心材料を明確に示す。
- 障害やエラー時は、回復経路と状況に合ったコミュニケーションを用意する。

**誤用**: 最後だけ演出して途中の苦痛を放置すること。重大なネガティブ体験は「良い締め」で相殺できない。

**検証質問**: ユーザーが翌日に一つだけ思い出すとしたら、どの瞬間になるか。

### 7. 美的ユーザビリティ効果 — 美しさは利用を助けるが、欠陥も隠す

**意味**: 見た目が美しい製品は、実際以上に使いやすいと評価されやすく、軽微な問題への寛容さも高まりやすい。

**設計への変換**:

- 視覚的な一貫性、階層、余白、タイポグラフィを機能品質として扱う。
- 第一印象が安心と理解を支えるようにする。
- ユーザビリティ評価では発言だけでなく、完了時間、失敗、迷い、行動を観察する。
- 見た目の異なるプロトタイプを比較するときは、美的印象による評価の歪みを考慮する。

**誤用**: 美しさで機能上の問題を覆い隠すこと。また、美観を装飾量と混同しない。

**検証質問**: 「好き」という評価とは別に、実際に迷わず完了できているか。

### 8. フォン・レストルフ効果 — 差異を使って一つの重要事項へ注意を向ける

**意味**: 同質な要素の中で異なるものは認識・記憶されやすい。

**設計への変換**:

- 主要CTA、警告、選択中の状態など、本当に重要な要素だけを際立たせる。
- 色だけに依存せず、形、サイズ、位置、ラベルを組み合わせる。
- 価格表や比較表では、強調がユーザー利益と一致しているか確認する。
- 動きによる強調は、モーションに敏感な人への影響と設定を考慮する。

**誤用**: 複数要素を同時に強調すること。全員が叫ぶ画面では、誰の声も届かない。

**検証質問**: 5秒見たユーザーが、最重要の操作を正しく答えられるか。

### 9. テスラーの法則 — 本質的な複雑さを作り手が引き受ける

**意味**: どのシステムにも除去できない複雑さがあり、それをユーザーか、設計・開発側のどちらかが負担する。

**設計への変換**:

- 既知情報の自動入力、推奨、検証、変換をシステム側で行う。
- 高度な機能は段階的開示で必要時に提供する。
- 決済や設定では、内部構造ではなくユーザーの目的に沿った言葉と順序を使う。
- 自動化の誤りが大きな損害になる場合は、確認・取消・説明可能性を残す。

**誤用**: すべてを自動化し、ユーザーの理解や制御を奪うこと。複雑さを隠すことと、説明責任をなくすことは別である。

**検証質問**: この手間は本当にユーザーにしかできないのか、それとも組織がコストを転嫁しているだけか。

### 10. ドハティのしきい値 — 応答の速さと進捗の可視化を設計する

**意味**: システム応答が十分に速いと、ユーザーの注意と作業の流れが維持される。本書では約0.4秒が代表的なしきい値として扱われる。

**設計への変換**:

- 性能をエンジニアリング指標だけでなくUX要件として定義する。
- 即時応答できない場合は、操作受付、進捗、残り時間、結果を明確に返す。
- スケルトン、段階的表示、楽観的更新は、実態を偽らない範囲で体感待ち時間を減らすために使う。
- 長い処理は中断・再開・バックグラウンド化を検討する。

**誤用**: アニメーションで実際の遅さを隠すこと。フィードバックは性能改善の代替ではない。

**検証質問**: クリック後に「受け付けられたか分からない時間」が存在していないか。

## 原則を実装へ変換する方法

本書が提示する有効な型は、心理学用語をそのままチームルールにせず、次の3層へ変換することだ。

```text
チームの目標
  ↓
人間行動についての観察・心理学的原則
  ↓
画面、フロー、コンテンツ、検証方法についての具体的ルール
```

例：

```text
目標: 初回ユーザーが迷わず主要タスクを完了できる
観察: 慣れたパターンは学習負荷を下げる（ヤコブの法則）
ルール:
- 標準的なナビゲーションとフォームパターンから始める
- 独自操作には可視ラベルを付ける
- 初見ユーザー5名以上で理解可能性を確認する
```

良いデザイン原則には、次の条件がある。

- チームの価値とユーザーの目的を表している。
- 特定画面に限定されず、複数の判断へ使える。
- 原則同士が競合したときの優先順位を議論できる。
- 観察可能なルールと検証方法へ落とせる。
- 永久の真理としてではなく、学習に応じて更新できる。

## 法則間の緊張関係

法則は単独最適化しない。実務では次の衝突が起こる。

| 緊張関係 | 判断基準 |
|---|---|
| ヤコブ × 独自性 | 独自性が主要目的の達成を明確に改善し、テストで理解可能なら慣例から外れる |
| ヒック × 発見可能性 | 削除ではなく分類・段階化を優先し、必要な機能へ到達できる状態を守る |
| ポステル × 安全性 | 軽微な表記揺れは寛容に扱い、金銭・権限・削除など不可逆操作は確認する |
| テスラー × 自律性 | システムが手間を引き受けつつ、ユーザーに結果の理解・修正・取消手段を残す |
| ドハティ × 正確性 | 受付フィードバックは即時に返し、確定していない結果を確定表示しない |
| 美的効果 × 検証 | 主観評価だけで合格にせず、行動・失敗・完了時間を測る |
| 摩擦削減 × 倫理 | 安全、熟考、同意、節度に必要な摩擦は意図的に残す |

## 倫理と説明責任

心理学の理解は、支援にも操作にも使える。変動報酬、無限スクロール、社会的比較、通知などは、ユーザーの目的より事業KPIを優先すると、注意や時間を搾取する仕組みになる。

設計レビューでは次を確認する。

- ユーザーの目的と事業目標は一致しているか。
- 利用時間や反復回数の増加を、価値の増加と誤認していないか。
- 同意、停止、解約、通知オフが取得・開始と同程度に理解しやすいか。
- ハッピーパス以外の失敗、依存、誤操作、脆弱なユーザーを検討したか。
- 定量データだけでなく「なぜ」と生活への影響を質的調査で確認したか。
- チームと調査対象に、盲点を発見できる多様性があるか。
- エラー防止、プライバシー、熟考のために必要な摩擦を残しているか。

## Brainbaseでの利用方法

### プロダクトレビュー

レビュー対象ごとに全法則を機械的に採点するのではなく、ユーザーの主要タスクに関係する法則を3つまで選び、次の形式で記録する。

```text
ユーザー目的:
観察した事実:
関連法則:
仮説:
変更案:
成功指標:
ガードレール指標:
必要な定性検証:
```

### Story・仕様

受け入れ条件には見た目だけでなく、認知・操作・応答・倫理の境界を入れる。

- 認知: 初見で主要操作と現在状態を説明できる。
- 操作: 対象サイズ、間隔、キーボード操作、エラー回復を確認できる。
- 応答: 操作受付が即時に分かり、長時間処理には進捗がある。
- 記憶: 画面をまたぐ情報の暗記を要求しない。
- 倫理: 取消、解約、通知停止、プライバシー設定が隠されていない。

### QA

```text
- [ ] 標準パターンから外れる箇所に理由と検証証拠がある
- [ ] 主要ターゲットが十分大きく、隣接操作と区別できる
- [ ] 情報が意味のある単位で構造化されている
- [ ] 選択肢の意味と推奨理由が分かる
- [ ] 入力揺れ、長文、多言語、文字拡大、異常系に耐える
- [ ] エラー、完了、終了時の体験が設計されている
- [ ] 美観とは別にタスク成功を検証している
- [ ] 強調対象が一意で、色や動きだけに依存しない
- [ ] システム都合の複雑さをユーザーへ転嫁していない
- [ ] 受付、進捗、成功、失敗が適時に通知される
- [ ] 必要な安全摩擦とユーザーの自律性が保たれている
```

## 使うときの注意

- 「法則だから正しい」ではなく、「この文脈で検証すべき仮説」として扱う。
- ターゲットユーザー、端末、能力、文化、利用環境によって結果は変わる。
- 成功指標だけを最適化せず、誤操作、離脱、後悔、苦情、通知停止、解約困難などのガードレールも見る。
- 原著の事例や技術状況は時間とともに古くなる。原則と具体例の鮮度を分けて扱う。
- 重要な設計判断では、本書の要約だけでなく、ユーザー調査、アクセシビリティ標準、プラットフォームガイドライン、現行の実装証拠を確認する。
