## エグゼクティブサマリー

UX戦略は、美しい画面を作る方法ではない。何を、誰のために、なぜ作り、どのように価値と収益を生むかを、実装前から証拠に基づいて判断するプロダクト戦略である。

本書の中心は次の反復ループにある。

```text
顧客と課題の仮説
  ↓ 顧客発見
市場と競合の調査・分析
  ↓ 機会領域の特定
バリューイノベーションと最重要機能
  ↓ ストーリーボード
ラピッドプロトタイプ
  ↓ 定性実験・定量実験
検証、ピボット、継続、または中止
```

設計や開発の開始は、アイデアへの確信ではなく、もっとも危険な仮説を低コストで検証したあとに置く。戦略は一度作って終わる計画書ではない。市場、技術、顧客、事業目標が変わる限り、プロダクトの終了まで更新し続ける。

## UX戦略の4つの基本要素

### 1. ビジネス戦略

企業がどう価値を作り、届け、獲得し、競争優位を維持するかを定める。

確認すること:

- 顧客セグメントとアーリーアダプターは誰か。
- 顧客が抱える重要な問題は何か。
- コスト優位と差別化のどちらで戦うか。
- 価値を誰が受け取り、誰が支払うか。
- チャネル、顧客関係、収益、コスト、主要資源、主要パートナーは成立するか。
- プロダクトのUXが獲得、維持、収益へどう寄与するか。

ビジネスモデルキャンバスやリーンキャンバスは完成した計画書ではなく、検証待ちの仮説を一枚に外在化する道具として使う。

### 2. バリューイノベーション

競合より少し良い機能を増やすのではなく、顧客が強く必要とする価値と、持続可能な事業価値を同時に作る。

確認すること:

- 顧客の古いメンタルモデルを変えるほど明確な便益があるか。
- 主要用途と最重要機能を一言で説明できるか。
- 競合の模倣ではなく、他市場の優れたパターンを再構成できるか。
- 機能だけでなく、価格、流通、収益モデル、顧客関係も差別化されているか。
- 独自性が新奇さだけでなく、顧客の成果につながっているか。

### 3. 検証をともなうユーザー調査

共感や観察だけで終わらず、顧客、課題、価値提案、機能、ビジネスモデルについての仮説を、実際の対象者との接触で判定する。

確認すること:

- 調査前に検証したい仮説と成功基準を定義したか。
- チームに都合のよい人ではなく、対象セグメントを募集したか。
- 誘導せず、現在の行動、代替手段、痛み、支払いについて聞いたか。
- 発言だけでなく、操作、迷い、感情、行動を記録したか。
- 結果が仮説を否定したとき、ピボットまたは中止できるか。

### 4. フリクションレスなUXデザイン

ユーザーが目的を達成するまでの不要な認知・操作・感情的負荷を減らす。成果物を作ること自体ではなく、獲得、利用、継続、収益につながる体験を作る。

確認すること:

- 最重要機能へ直結した流れになっているか。
- ユーザーが現在地、次の行動、結果を理解できるか。
- 競合調査と顧客調査で得た知見が画面とフローへ反映されているか。
- 短期的なコンバージョンのために信頼や自律性を損ねていないか。
- 実際のユーザーが価値を感じるかをプロトタイプで確認したか。

4要素は単独では成立しない。優れたUIでも需要がなければ失敗し、強い需要があってもビジネスモデルがなければ続かず、独自性があっても使えなければ採用されない。

## 実務プロセス

### フェーズ1: 最初のバリュープロポジションを定義する

1. 最初に狙う顧客セグメントを一つ選ぶ。
2. その顧客が現在抱える最大の問題を仮置きする。
3. 暫定ペルソナを作り、既知の事実と推測を分ける。
4. プロブレムステートメントを作る。
5. 顧客発見インタビューで、顧客と問題の存在を検証する。
6. 学びに基づいて価値提案、顧客、問題を再評価する。

暫定ペルソナは調査結果ではない。チームの推測を見える形にし、何を確かめるべきかを共有するための出発点である。

顧客発見ではソリューションを売り込まない。現在どう対処しているか、どの程度の頻度と深刻さで困るか、既存手段へ何を支払っているかを確かめる。

### フェーズ2: 競合を調査する

競合は、同じカテゴリの製品だけではない。同じ顧客の同じ問題を別の方法で解く代替手段も含む。

調査対象:

- 直接競合、間接競合、潜在競合。
- 顧客セグメントと価値提案。
- 主要機能、ユーザーフロー、オンボーディング。
- 価格、課金単位、収益モデル。
- 集客チャネル、評判、レビュー、離脱理由。
- 組織、資金、提携、技術、運用上の強みと制約。
- 成功例だけでなく、終了・縮小・失敗した事例。

競合を真似るためではなく、市場の常識、空白、失敗、顧客の期待を学ぶために調査する。

### フェーズ3: 競合情報を分析する

1. データをスキミングし、最大値、最小値、外れ値、反復パターンを印づける。
2. 比較可能な軸へグループ化する。
3. ベンチマークとSWOTで、市場の強さ、弱さ、機会、脅威を整理する。
4. 発見、意味、推奨、次の検証を競合分析ブリーフへまとめる。

調査は事実収集、分析は意思決定へ使える示唆の生成である。情報の羅列で終わらせない。

判断の目安:

- レッドオーシャン: 飽和市場。参入理由、顧客、価値提案の再考が必要。
- パープルオーシャン: 既存市場に未解決の空白がある。差別化仮説を実験する。
- ブルーオーシャン: 新しい市場機会。ただし需要と行動変容の難しさを検証する。

### フェーズ4: バリューイノベーションを可視化する

最重要機能とは、機能一覧の最上位ではなく、価値提案をユーザーが体験できる決定的な仕組みである。

進め方:

1. 顧客の主要用途を一つに絞る。
2. 競合の機能比較から必須、過剰、未充足を見つける。
3. 他分野のUXインフルエンサーから、機能、操作、事業モデルのパターンを借りる。
4. それらを組み替え、独自の価値仮説を作る。
5. 利用前、利用中、利用後をストーリーボードで描く。

ストーリーボードには、画面より先に顧客の状況、動機、接点、行動、結果を描く。これにより、価値のない機能を作り込む前に体験全体を議論できる。

### フェーズ5: ラピッドプロトタイプで実験する

目的は製品を完成させることではなく、価値提案を体験可能な形にして危険な仮説を検証することにある。

原則:

- 最重要機能と検証対象だけを作る。
- 本物らしさは、参加者が判断できる最低限に留める。
- コードが不要なら書かない。
- 画面遷移、紙、動画、疑似データ、手動運用を使ってよい。
- 各画面がどの仮説を検証するか明記する。
- 実験中に壊れない程度の操作経路とリセット手段を用意する。

プロトタイプの完成度を上げすぎると、変更への心理的抵抗とサンクコストが増える。検証に不要な品質は後回しにする。

### フェーズ6: オンラインユーザー調査を行う

#### 計画

- 仮説、成功基準、対象者、人数、募集条件を決める。
- スクリーナー、同意、台本、記録方法、役割分担を用意する。
- 価値提案、ビジネスモデル、最重要機能を別々に判定できる質問を作る。
- まず少人数で実施し、シグナルが弱ければ追加調査する。

#### 実施

- セッションの目的と録画・記録の扱いを説明する。
- 「正解」を教えず、参加者に考えながら操作してもらう。
- 言葉、表情、沈黙、迷い、操作、質問を記録する。
- 価格や利用意向は仮定の発言だけでなく、現在の支出や具体的行動で補強する。

#### 分析

- 仮説単位で支持・不支持・不明を分類する。
- 成功基準と比較し、サンプル数と限界を併記する。
- 予定外の発見と、強い反応があった箇所を残す。
- データ、解釈、推奨アクションを分けて報告する。

少人数の割合を市場全体の統計的事実として扱わない。初期調査の数字は、次の判断と追加実験に使う方向性のシグナルである。

### フェーズ7: ランディングページ実験で定量シグナルを得る

定性調査で「なぜ」を学んだあと、ランディングページと広告で、より多くの対象者が実際に反応するかを測る。

実験前に固定すること:

- 検証する価値提案、顧客セグメント、価格または行動。
- 流入チャネルと広告メッセージ。
- 主CTAとコンバージョンの定義。
- 成功基準、実験期間、予算、停止条件。
- 虚偽表示を避けるための説明と、取得データの扱い。

見る指標:

- 広告の反応率と獲得単価。
- ランディングページ到達後のCTA率。
- 登録、予約、購入意思、支払いなどコミットメントの強さ。
- セグメント、メッセージ、価格、チャネルごとの差。
- 離脱点と、その後の定性フォローアップ。

クリックは需要の証明ではない。行動の重さに応じて証拠の強さを評価する。

## 判断マトリックス

| 検証結果 | 次の行動 |
|---|---|
| 顧客が違う | 顧客発見へ戻り、セグメントを変更する |
| 問題が弱い | 問題仮説を変更するか中止する |
| 価値提案が弱い | 競合分析と価値革新へ戻る |
| ビジネスモデルが弱い | 価格、支払者、課金単位、チャネルを再設計する |
| 最重要機能が弱い | ストーリーボードとプロトタイプを修正する |
| 定性のみ支持 | 定量実験で対象を広げる |
| 定量のみ支持 | 理由と継続利用可能性を定性調査で確認する |
| 両方支持 | 証拠の限界を明記し、段階的な実装へ進む |
| 結果が不明 | 質問、募集条件、実験設計を直して再実施する |


```text

```

### Story・仕様への変換

- Storyにはユーザーだけでなく、検証済みの問題と期待成果を記載する。
- Architectureには事業モデル、運用、データ、チャネルを含む体験全体の制約を反映する。
- Specには最重要機能と、その価値が成立する最低条件を定義する。
- Taskはプロトタイプ／実験と製品実装を分ける。
- Gateには「作れた」証拠ではなく、対象顧客が価値を得た証拠を置く。
- 仮説が否定された場合のピボットまたは中止条件を事前に記録する。

### QA・レビュー

```text
- [ ] 対象顧客と問題は実在する行動証拠で確認されている
- [ ] 事実、推測、仮説、意思決定が区別されている
- [ ] 直接・間接競合と現在の代替手段を確認した
- [ ] 価値提案と最重要機能を一文で説明できる
- [ ] 収益モデルと顧客価値が矛盾していない
- [ ] 最重要の不確実性を最小コストで先に検証した
- [ ] プロトタイプが完成品化していない
- [ ] 調査対象者が顧客セグメントに合っている
- [ ] 誘導質問やチーム内都合の良い解釈を避けている
- [ ] 成功基準、停止条件、ガードレールを実験前に決めた
- [ ] 定性と定量の役割を混同していない
- [ ] サンプル数と証拠の限界を明記した
- [ ] 否定的結果に対するピボット・中止判断がある
- [ ] 獲得だけでなく継続利用とユーザー成果を測る
- [ ] ダークパターン、虚偽表示、不要な個人情報取得を避けている
```

## よくある誤用

- ステークホルダーのビジョンを検証済み要件として扱う。
- ペルソナを調査せず、想像上の人物像を精緻化する。
- 競合調査を機能一覧のコピーにする。
- アイデア出しの量を価値革新と混同する。
- MVPを「品質の低い製品」または「小さな正式リリース」と解釈する。
- プロトタイプへ全機能を実装する。
- 参加者の好意的な発言だけで需要を証明したと考える。
- 少人数調査の割合を市場全体へ一般化する。
- クリックやメール登録だけで支払い意思を断定する。
- 実験が失敗してから成功基準を変更する。
- コンバージョン最適化で長期的な信頼を損なう。
- 戦略を一度作るロードマップやスライドだと考える。

## 本書を使うときの注意

- 本書の具体的なサービス、ツール、広告環境、価格は2021〜2022年頃の状況を含む。現行情報は別途確認する。
- 調査で得た個人情報、録画、発言は同意、目的、保管期間、アクセス権を定める。
- 初期実験はリスクを減らすが、製品市場適合や事業成功を保証しない。
- 仮説を否定する証拠は失敗ではなく、実装費を使う前に得た価値ある学習として扱う。
- フリクションをすべてなくさない。安全、同意、確認、熟考に必要な摩擦は残す。
- 顧客獲得だけでなく、ユーザー成果、継続性、社会的影響を確認する。
- 調査と実験は一度で完了せず、プロダクトのライフサイクル全体で繰り返す。
