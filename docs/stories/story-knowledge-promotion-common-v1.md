# 本人が承認した個人の記憶と、組織内で承認された候補だけを、同じ昇格処理で組織のGraphへ入れる

## 利用者成果

- 組織で働く人として、個人KG v1に書いた記憶のうち、組織に役立つものを要約して共有を申請し、本人として承認したものだけを組織のレビューへ回したい。承認していない記憶や原文が組織へ出ていかないと確信したい。
- 組織のGM・CEOとして、議事録の観察やタスクの候補のように組織内で生まれた候補を、承認したものだけ組織のGraphへ正式に登録したい。定期実行が勝手に登録しないこと、却下したものが後の検索に混ざらないことを確かめたい。
- どちらの経路でも、Graphに入った事実から、元の記憶または候補・承認した人・承認記録・対象の版までたどりたい。

## 背景と決定

- 横断ADR（`brainbase-project` ADR-006「D4・D12: 個人共有と組織候補の昇格」）は、個人共有を「本人承認→組織レビュー→共通昇格サービス→組織Graph」、組織候補を「組織内の承認→同じ昇格サービス→組織Graph」と決め、承認の出所を分けたまま同じサービスを通すとした。
- ADR-003 D1と`brainbase-unson`の所有台帳（`knowledge-event-and-memory-promotion-common`）は、正規化・本人同意・証跡・Graph変更案の生成をOSSの共通処理、組織レビューと権限照合を`brainbase-organization`の統制とした。
- 2026-10-01、佐藤が選択肢カードで次を決めた。
  - 届け方：共通処理をOSS、組織レビューと権限照合を組織版のpackageに置き、`brainbase-unson`は組立てとv1の読み口・DB・経路だけを持つ。
  - 組織候補の承認者：同じ組織・同じプロジェクトのGM・CEOが人としてログインして承認する。候補が「判断」のときは、その領域の決定権をGraphで確認できる人に限る。定期実行とサービス主体は承認できない。
- この処理は保存先・認証・役職の判定を持たない。保存、個人KG v1と候補の読み取り、知識イベントの記録、Graphへの書込み、組織の審査規則は差し込み口として受け取り、差し込まれていなければ止まる。

## 受入条件

- [x] AC-01: 個人共有の申請は、認証済みの本人が持つ個人KG v1のイベントだけを対象にする。別人・別組織のイベントは「見つからない」とし、要約・件名・正規化済みの内容から秘密・メールアドレス・個人のパスを拒否する。原文は申請に入れない。
- [x] AC-02: 組織候補の申請は、同じ組織・同じプロジェクトの、昇格レビュー待ちの候補だけを対象にする。却下・期限切れ・隔離済み・撤回済みの候補は申請できない。
- [x] AC-03: 個人共有は、本人が承認するまで組織レビューへ進まない。本人以外は本人承認できず、本人承認では正規化済みの内容のハッシュが申請時と一致することを求める。
- [x] AC-04: 組織のレビュー（個人共有）と組織内の承認（組織候補）は、差し込まれた組織の審査規則が許したときだけ進む。規則が無ければ止まる。人以外の主体は承認できず、個人共有では本人と同じ人は組織レビューできない。組織候補は本人承認を受け付けない（本人承認を装わない）。
- [x] AC-05: 却下（本人・組織）は終わりの状態で、Graphへ書かない。却下の後に承認は受け付けない。
- [x] AC-06: 承認のときは、対象の記憶・候補が申請時と同じ版で有効かを読み直し、違えば「古い版」として止め、Graphへ書かない。
- [x] AC-07: 承認されたときだけ、組織の知識イベントの記録、正規化済みの内容のGraphへの書込み、系譜の記録、申請の状態の更新を同じトランザクションで行う。個人の原文と要約はGraphへ複写しない。
- [x] AC-08: 系譜には、承認の種類、元の記憶または候補とその版・証跡のハッシュ、申請、本人承認と組織承認の受領記録、組織の知識イベント、Graphのエンティティ、テナント、プロジェクトを残す。
- [x] AC-09: 同じ内容の申請と同じ判断の再試行は、同じ結果を返し二重に書かない。版（revision）の食い違いは409で止める。
- [x] AC-10: 個人共有の本人承認と組織レビューの受領記録は、既存の二段階昇格（`brainbase-unson`）と同じ計算で作り、移設後も既存の受領記録を検証できる。

## 対象外

- 旧Personal Vault（`personal_knowledge_events`）と旧候補（`memory_candidates`内の旧個人KG）の自動移行（ADR-003 D4）。
- 共有の取消・権限失効の将来の取得への反映、削除のAPI。
- 認証・テナント分離・役職と決定権の判定（組織版）、DBのスキーマとHTTPの経路（組立て側）。
- 本番への配備。
