# 同じサービスの複数のアカウントを、接続ごとに分かれた認証・読んだ位置・状態で同期できる

会議ソースをつなぐ利用者と、それを組み込む組織版の開発者として、同じPlaudやTactiqを複数のアカウントでつないでも、認証・どこまで読んだか・失敗の状態が接続ごとに分かれていてほしい。ある接続の進みや失敗が、別の接続に混ざらないようにしたい。

## 完成時の利用者成果

接続ごとに「確認で実際に使えた能力」「最後の成功と失敗」「全文待ちの会議」が分かれて見える。接続を切ると、その接続の同期と資格情報だけが止まる。接続の実行部分（`ConnectionRuntime`）を別の実装に差し替えても、読み出し・同期・受け渡しの結果は変わらない。

## 受入条件

- [x] AC-01: 接続の記録の型を公開する。接続IDはBrainbaseが発行し、外部の接続基盤のIDは参照（`backend_ref`）としてだけ持つ。記録に秘密値を入れない。
- [x] AC-02: `ConnectionRuntime`（確認・ツールの実行・切断）と、MCPのSDKを使う`NativeMcpRuntime`を公開する。資格情報は差し込み口から受け取り、応答・ログ・状態・エラーにtokenを出さない。今のファイル1つのOAuthの保存は、差し込み口の実装の一つにする。
- [x] AC-03: 確認は、認証だけでなく一覧と全文を実際に読めることまで確かめ、使えた能力だけを返す。確認が通るまで「接続済み」にしない。認可切れは再認可が要る状態として返す。
- [x] AC-04: 同期の状態（どこまで読んだか、全文待ちの会議と理由と次に試す時刻、最後の成功・試行・失敗）を接続ごとに持つ。全文待ちの会議は、全文が取れるか取得できないことが確定するまで、取り込み済みにしない。
- [x] AC-05: 1回の同期でproviderの呼び出しが失敗したら、その接続の回を「失敗」として理由を残す。「新しい会議が無い」と記録しない。
- [x] AC-06: 同じ会議を二度渡さない。キーは「接続・provider・会議ID」とし、全文の`digest`が変わったときは新しい版として渡す。別のproviderで録った同じ会議の判定は、同じ持ち主・同じテナントの中だけで行い、全文のハッシュだけで一つにしない。
- [x] AC-07: 同じproviderの接続を2つ並べた試験で、資格情報・読んだ位置・全文待ち・失敗・受け渡しが互いに混ざらない。片方を切っても、もう片方は続く。
- [x] AC-08: 止まっていた期間を指定して取り直しても、すでに渡した会議を重複させない。
- [x] AC-09: OAuthの開始と完了は、公開済みの組織接続の共通部品（`@unson/brainbase-mcp/organization-connection`）に、MCPのOAuth（サーバーの探索・動的なクライアント登録・PKCE・token交換）を行う差し込みを足して使う。新しいOAuthの仕組みは作らない。

## 範囲と境界

- 置き場はOSSの公開package。同期の状態・接続の記録・資格情報の保存先、テナントと持ち主の認可、同期を定期的に動かす場所は、差し込み口として利用側（組織版）が持つ。
- 取り込み先（Manaの議事録の受付など）は差し込み口で受け取り、このStoryでは決めない。
- Nangoの実装は作らない。差し替えの検証は組織版の`story-organization-meeting-source-nango-trial-v1`で行う。
- OSS単体の利用者向けの接続画面と、nativeの議事録への取り込みは対象外（後続の候補）。

## 開発判断

全体はSIMPLIFICATION。大きなプラグイン基盤は作らず、2つの境界（`ConnectionRuntime`・`MeetingSourceReader`）と、接続ごとの状態だけを足す。今の同期は状態とtokenをproviderごとに1つのファイルで持ち、本番と手元で別々の状態になっていて、どちらも正本ではない。

全体の分割と根拠: [会議ソース（Plaud・Tactiq）の接続と取り込み：引き継ぎ設計](../../../brainbase-project/docs/architecture/meeting-source-connection-design.md) §5・§8。
