## 基本モデル

LLMアプリケーションは、プロンプト文面だけで品質が決まらない。ユーザーの問題をモデルが扱える表現へ変換し、必要な文脈を選び、生成結果をユーザーの目的へ戻し、結果から次の入力を作るループとして設計する。

```text
ユーザーの問題
  → 問題の明確化・構造化
  → 静的指示 + 動的コンテキスト + 例
  → LLMによる補完
  → 検証・変換・ツール実行
  → ユーザーの成果
  → オフライン／オンライン評価で改善
```

## 実務原則

### 1. 補完させたい文書を設計する

- 命令を重ねるより、望ましい出力が自然な続きになる文脈を作る。
- 役割、目的、入力、制約、出力形式を矛盾なく並べる。
- 曖昧な依頼は、モデルに渡す前にアプリケーション側で明確化する。
- Few-shot例は説明ではなく、形式と判断パターンを示す実演として使う。

### 2. コンテキストには優先順位をつける

- 静的な規則と、検索・ユーザー状態・ツール結果などの動的情報を分離する。
- 関係の薄い情報を大量に渡さない。重要な情報が埋もれることも品質劣化である。
- RAGは検索結果を貼る機能ではない。取得、順位付け、圧縮、配置、引用検証までが一つの設計である。
- 情報源、鮮度、権限、取得失敗を回答から追跡できるようにする。

### 3. 出力形式を契約にする

- 後段が機械処理する値は、自由文ではなく構造化出力やツール呼び出しにする。
- 必須フィールド、型、列挙値、未知時の表現、再試行条件を先に定義する。
- パース成功を意味的正しさと混同しない。根拠、数量、参照先を別途検証する。
- ユーザー提示値とモデル生成値を区別し、モデルに不要な再生成をさせない。

### 4. 複雑な仕事はループとワークフローへ分ける

- 一回の巨大プロンプトより、計画、検索、生成、検証、修正を小さな段階へ分ける。
- 各段階の入力・出力・停止条件を明示する。
- 会話エージェントには状態、利用可能なツール、権限、最大反復数、失敗時の出口を持たせる。
- ツール実行結果を信用しすぎず、対象、成功条件、副作用を検証する。

### 5. 評価を先に設計する

- 開発中は固定データセットによるオフライン評価で回帰を検出する。
- 本番では成功率、修正率、離脱、再試行、コスト、レイテンシなどをオンライン評価する。
- 主観評価だけでなく、タスクごとの受け入れ条件と失敗分類を作る。
- モデル変更、プロンプト変更、検索変更、ツール変更を別々に比較できるログを残す。
- 出力本文や機密情報を不用意にログへ残さず、追跡可能性とデータ最小化を両立する。

## 改善ループ

1. ユーザーが達成したい成果と失敗コストを定義する。
2. 代表ケース、難例、拒否すべきケースを評価セットへ入れる。
3. 生成前後の各境界を計測し、失敗が検索・指示・生成・検証・UIのどこにあるか分ける。
4. 一度に一つの変数を変更してオフライン評価する。
5. 安全な範囲で段階的に公開し、実利用の行動指標を確認する。
6. 失敗例を評価セットへ戻し、再発防止条件を追加する。

## アンチパターン

- 長いプロンプトを品質の代理指標にする。
- モデルが知っているはずだとして、必要な業務文脈や現在情報を省く。
- ハルシネーション対策を「嘘をつくな」という一文だけで済ませる。
- 一回の成功例を品質証明にする。
- モデルのもっともらしい自己評価を採点結果として使う。
- 失敗をすべて再試行で隠し、どの生成境界で失敗したか記録しない。

## Brainbaseへの適用

- Graph、owning repo、Drive、個人コンテキストの探索順と権限を、動的コンテキスト取得の契約にする。
- `見つからない`、`取得失敗`、`権限なし`、`未確認`を異なる状態として回答へ伝える。
- チーム知識では、回答本文とは別にソースID、取得時刻、抽出方法、検証状態を保持する。
- 改善時は回答だけでなく、検索候補、採用ソース、生成、検証、再試行の境界を評価する。
