# 議事録の判断・訂正と記憶循環

## 目的と所有
Manaは議事録を作成する時点で実際の判断を記録する。Brainbaseは取得した組織知識の根拠と、後から届く訂正・検証結果を保持する。おやすみは記録済みの経験を照合・圧縮して検索可能な学びへ変え、レトロは仕組みの変更案へまとめる。

| 対象 | 所有する正本 |
|---|---|
| 実行したノード、試行、分岐、結果 | Manaの既存実行状態とRun Receipt |
| 検索した範囲、候補、Graph参照 | Brainbase context receipt |
| 正式な用語・組織事実 | Graph SSOT |
| 訂正、利用結果、再検証の根拠 | Brainbaseの既存知識イベント・feedback経路 |
| 日次照合・週次改善案 | 既存Routine RunnerとRoutine Cycle Executor |

実行履歴は短い判断理由と証拠を記録する。モデル内部の思考過程を収集しない。定義済みDAGと実際に通った経路を区別し、未実行ノードをcompletedで埋めない。

Manaは実際のランタイム境界を `mana_meeting_minutes_runtime.v1` として記録する。定義はManaリポジトリの `docs/architecture/meeting-minutes-runtime-judgments.md` に置く。既存の `meeting_pack_graph_ssot_playbook` は関連する上位の判断定義として区別する。Graph側のplaybook実行そのものとは別であり、現在のMana経路は `graph_playbook_status=not_executed` とする。Graph昇格や人間レビューのゲートを実行したとは記録しない。参照定義とランタイムに差があること自体を、改善対象として辿れるようにする。

## 通信と再開

1. Manaは案件と会議文脈を、既存の認証済みcontext receipt作成経路へ渡す。入力の案件名を権限として使わず、署名済みtenant/projectの範囲で検索する。
2. Brainbaseは候補・参照元・検索不足を返す。大量のdecisionが用語候補の枠を奪う平坦な切捨てを廃止する。
3. Manaは実行境界で状態を永続化する。再開時は以前の試行を保持し、現在の実行結果と区別する。
4. 既存のRun Receipt送達を使い、Brainbaseの記憶入力へ接続する。再送は同じ実行を増殖させず、配送不能は未確認として残す。
5. 後日の訂正は元の実行と判断ノードへ参照で接続する。元の証拠を上書きしない。

## 夜・朝・週次

- おやすみは外部Slack/GitHub/文字起こしを再探索しない。正規化済み記録を照合し、品質未確認・訂正・検索不足を持ち越す。圧縮しても元のrun、node、DAG版、根拠を辿れるようにする。
- おはようは既存の例外表示を使い、対応が必要な未解決だけを示す。
- レトロは件数だけで変更を決めず、根拠と原因の分類を持つ候補を出す。原因候補は、定義不足、未実行、検索不足、判断・生成誤り、観測不足として区別する。断定できなければ未確認とする。
- 正式用語の昇格と、DAG・コードの変更は既存のレビュー経路を使う。定期実行に本番変更権限を与えない。
- 重大な不具合は週次を待つ条件を付けず、通常の障害対応で扱う。

品質が未確認であることと、利用者の対応が必要であることは分ける。訂正や具体的な取得失敗がない新規議事録に、再検証がまだないという理由だけで修正PRや朝の警告を要求しない。未確認という記録は残し、問題が見つかった時点で原因調査と再検証へつなぐ。

## 閉鎖条件
配信成功、ログ保存成功、指摘なし、修正commitだけでは品質改善を確認済みにしない。訂正に対応する変更版と、元の失敗例および別事例の再検証結果への参照が必要。自動検査で確認した構造的な整合性と、実会議での正しさを分ける。

## 運用上の責任

| タイミング | 実行主体と確認すること |
|---|---|
| 議事録作成時 | Manaが判断と参照を保存し、既存のRun Receipt経路でBrainbaseへ渡す。取得不足を生成結果に隠さない。 |
| 利用者の訂正時 | 対応エージェントが対象runと該当ノードを読み、既存のknowledge feedbackへ訂正と根拠を記録する。対象不明なら原因を断定しない。 |
| おやすみ | 既存Routine Runnerが記録済みの経験を照合する。取り込み失敗や根拠不足は未確認として残す。 |
| おはよう | 未解決のうち対応が必要なものを既存の例外表示へ引き継ぐ。未確認を毎朝無条件で大量通知しない。 |
| レトロ | 根拠のある原因候補から最大3件の仕組み変更案を作る。担当エージェントがStory／PRへつなぎ、正式な判断定義はレビュー後に変更する。 |
| 修正後 | 元の失敗例と別事例を再検証し、変更版・結果・元の訂正への参照を記録する。確認できた範囲だけを閉じる。 |

既存コマンドは `.claude/commands/oyasumi.md`、`.claude/commands/ohayo.md`、`.claude/commands/retro.md` を使う。夜の開始を新たなcronに移したり、Slackの訂正を収集する別botを増やしたりしない。訂正の記録と承認後の変更・再検証は、対応エージェントの明示的な仕事として残す。

## 配備・ロールバック
Brainbaseの追加フィールド受入れを先に反映し、その後Manaの送信側を反映する。旧receiptは判断未確認として読める互換性を保つ。本番配備前に両PRの契約テストと回帰テストを確認する。障害時は送信側から旧版へ戻し、すでに保存した履歴は削除しない。

## 実会議での確認
承認済みの対象実行について、取得receipt、Manaのノード履歴、Brainbaseの日次入力、訂正、再検証を同じ参照で辿る。「アイテル」が正しく書かれたことと、そう判断した根拠が残ったことの両方を確認する。本番で未実行なら未確認のままとする。
