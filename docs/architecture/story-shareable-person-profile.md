# Story: Manaが共有を許可された人物情報だけで回答する

Slackの利用者として、Manaに人物について尋ねたとき、依頼者が閲覧でき、かつ返信先に開示できるプロフィールだけを根拠付きで回答してほしい。

## 受け入れ条件

- `brainbase_get_shareable_person_profile`をManaのMCPに追加する。
- 依頼者・テナント・workspace・app・返信先は署名済み実行コンテキストから取得し、モデル引数による上書きを拒否する。
- 対象は正確なSlack user IDから正本の人物IDへ解決する。名前による推測や曖昧候補の採用をしない。
- 返却候補は氏名・所属・役割のみ。項目ごとの明示的な閲覧許可と返信先への開示許可の積集合だけを返す。
- 開示設定なし、署名不正、権限失効、別テナント、対象不明の場合は情報を返さない。私的メモ・評価・契約情報等はモデルへ渡さない。
- 代理依頼者の権限が広くても返信先の開示範囲は広がらない。
- Manaは配送直前に、実際の配送先と取得時の条件および最新の許可を再確認する。不一致の場合はプロフィールを含む生成済み回答を送信しない。
- 影響するテスト、1回のレビュー、通常のPR/CIを通し、Brainbase→Manaの順で配備して公開面から確認する。

## Spec / 境界

モデルの入力は`target_slack_user_id`のみ。実行コンテキストは信頼されたMCPプロキシが転送する。サービス認証は通信主体の認証に限定し、人物情報の開示許可を代替しない。

Brainbaseは署名と有効期限を検証し、正本の現在の依頼者・対象者・接続・組織/プロジェクトを確認する。人物プロフィールの共有設定は正本の明示的なポリシーのみを使う。既存の汎用Graph検索、CRM本文、個人KGへのフォールバックは禁止する。設定の追加や既存人物の共有範囲変更は本Storyに含めない。

返却値は固定スキーマとし、共有可能な項目、対象Slack ID、配送先とポリシーに結びつく検証情報を含む。エラーは固定コードとし、生のレコードや例外を返さない。Manaは取得結果を信頼された実行状態に保存し、配送時に再取得・比較する。権限変更、応答不明、配送先変更はfail closedとする。

## 検証

成功、設定なし、項目単位の拒否、代理依頼、actor/tenant/channel偽装、期限切れ・失効、曖昧な対象、配送時の変更、余剰引数と余剰返却フィールドをテストする。本番スモークでは個人情報をログ出力せず、ツール公開と拒否動作を確認する。

## 配備と復旧

BrainbaseのAPI/MCPを先に配備し、その後Manaの許可リストと配送前検証を配備する。旧クライアントは新ツールを呼ばない。復旧時はManaでツールを無効化してからBrainbaseを戻す。DBの人物情報・共有許可を自動移行しない。

APIの内部エンドポイントは`POST /api/v1/runtime/person-profile:read`。MCPはサービス認証と署名済みコンテキストを添えて呼ぶ。本番MCPの`BRAINBASE_TENANT_RUNTIME_API_URL`は同一ホストの内部runtime（`http://127.0.0.1:31016`）を指定する。公開Graph APIに人物の生データを取りに行く経路は追加しない。

共有設定は人物Graphレコードの`payload.shareable_profile`を使用する。`version: shareable-person-profile.v1`、正整数文字列の`revision`、`fields`配下の`name`/`affiliation`/`role`のみを受け付ける。各項目には`value`、閲覧者の正本人物ID一覧`reader_person_ids`、公開先の`workspace_id`/`channel_id`組一覧`audiences`が必要。設定がない既存人物は`unavailable`となり、従来の人物レコードから自動補完しない。

## 実装検証（2026-09-16）

Brainbase側はサービス22件、HTTP境界3件、Repository/環境配線6件、既存runtime回帰29件が成功。MCPの対象テスト13件とTypeScript検査・ビルドが成功。Repositoryの3つのSELECTは本番PostgreSQLで読み取り専用トランザクション内のEXPLAINを通過した。サービス/HTTP境界の独立レビューでブロッカーなし。配備後のAPI/MCPとMana側の配送検証は別途readbackする。

## 監査表示の復旧（2026-09-16）

利用者として、共有プロフィールの照会が成功した場合は、その実結果に一致する監査表示を見たい。成功を失敗と表示せず、実際の拒否・不明は成功へ置き換えない。

受け入れ条件:
- Claude/MCPの実際の応答形式で共有プロフィールの固定契約を検証し、対象Slack IDと取得結果を監査に表示する。
- 知識参照先の選択は、署名済み会社権限で確認されたプロジェクトに限定して実行できる。常駐MCPの静的プロジェクト設定を拡大しない。
- 無署名・改ざん・期限切れ・別プロジェクトの要求は既存境界に従って拒否する。
- プロフィールの共有範囲は変更しない。実失敗と未知の応答形式は警告を維持する。
- 回帰テスト、通常PR/CI、本番API/MCPの確認を行い、元Slackスレッドの新しい返信で本文と監査の一致を確認する。

Graphifyは対象worktreeのグラフがなく影響範囲は未確認。ファイル・呼び出し元・既存テストを直接確認して補完する。配備対象はBrainbaseのAPI/MCP/Host。既存のManaコンテナはリモートHostを呼ぶため、契約が変わらなければ再配備を要しない。

検証結果: 関連80件（MCP19、プロフィール25、Host1、既存参照先20、署名・権限境界とroute15）成功。MCP typecheck成功。新しい参照先選択は内部runtime APIで毎回署名と最新権限を確認し、canonical projectのtenant所有関係・有効状態まで照合する。

### 参照先照会の中継認証

- trusted provider forwarder は `brainbase_knowledge_resolve` にも署名付き Company Authority を保持し、専用ヘッダーとして MCP に転送する。
- profile の署名必須、他ツールの署名ヘッダー拒否、canonical project のサーバー注入を維持する。
- 下流の fresh authority 検証を通過した参照先照会のみ成功にする。

### 共有プロフィールの回答根拠

最新のGraph参照先解決後に取得した共有プロフィールは、開示された項目だけを部分的な人物根拠としてHostに記録する。reference_idsはdisclosure.target_person_idを使い、モデルはbrainbase_knowledge_evidence_recordで質問への十分性を別途判定する。未共有の所属・役割を推測せず、不足を明示する。失敗・未検証の応答は根拠にしない。
