# 医療版：患者情報の混入封じ込め設計（UR-030）

作成日: 2026-11-05 / UNS-470 / 状態: Draft・設計提案（未実装・運用未承認）

## 1. 目的・前提・スコープ外

UR-030 は要求台帳で「未決」。本稿では課題に転記された要求とスコープを参照する。要求台帳・環境一覧そのものの内容は未確認。

**Cloudflare は候補に残すが、患者情報が混じる経路での本番利用は未承認。** 公開仕様の確認は契約・医療情報取扱いの適合性確認や本番許可を意味しない。

本稿は入力経路、隔離境界、保持方針、サービス比較、承認条件を定める。実在の患者情報、音声、画像は用いない。ここでの保持期間は提案値であり、現行設定でも法定の診療記録保存期間でもない。診療記録の正本は対象外で、既存の医療機関の管理に従う。

[SECURITY.md](../../SECURITY.md) の local-first・外部バックエンド不要の境界を維持する。ただしローカル MCP の結果を外部 AI が受け取る場合も外部送信となる。local-first だけでは患者情報を安全に扱えると判断しない。本稿の隔離・出口制御が既存ランタイムで実装済みとは主張しない。

対象外: 製品コード変更、設定変更、配備、鍵操作、契約締結、削除実行、migration、外部サービスへのデータ投入。brainbase-unson は設定専用で変更しない。医療機関固有の権限・監査・運用 UI の将来実装は組織製品側の責務であり、OSS 単一所有者ランタイムへ追加しない。

## 2. 入力経路と残留先

以下は混入リスクの棚卸しであり、現環境で全経路が稼働しているという意味ではない。入口で停止しないと、検出前に外部サービスへ届く点に注意する。

| 経路 | 入口 | 経由する処理 | 残留しうる先 | 既定の制御 |
| --- | --- | --- | --- | --- |
| 外来の会話 | 端末マイク・録音機 | 録音、文字起こし、要約 | 録音端末、音声認識側、議事録 | 外部音声認識へ送る前に止める。承認済み閉域のローカル処理のみ候補 |
| 音声メモ・録音 | 手動取込・自動同期 | 音声変換、STT、話者識別 | クラウド同期、一時音声、文字列、モデルキャッシュ | 自動同期を入口にしない。取込許可リストと隔離 |
| 会議記録 | 議事録 bot・会議録画 | STT、要約、タスク化 | 会議 SaaS、検索索引、カレンダー、通知 | 医療会議は収集対象外。既存 SaaS 側の残留も別途確認 |
| チャット | Slack 投稿・DM・bot | connector、引用、要約 | Slack、アプリのキュー、通知、履歴 | 患者情報を Slack に貼らない。取得も許可範囲を限定 |
| メール | 本文・件名・添付 | 収集、MIME 展開、要約 | メール箱、転送先、スプール、検索 | 件名・アドレスも検査対象。自動転送しない |
| 添付ファイル | PDF・表計算・文書 | 展開、抽出、埋め込み | 原本、埋込画像、作業ファイル、ベクトル DB | メタデータ、隠しシート、コメント、埋込物も隔離検査 |
| スクショ・スキャン | 画像・画面共有 | OCR、サムネイル生成 | 画像、EXIF、OCR、プレビュー | 外部 OCR 前に止める。画像上の文字とバーコードも確認 |
| 手入力・貼り付け | フォーム・プロンプト | API、MCP、エージェント | ブラウザ保存、会話履歴、SSOT | 自動保存前に隔離。外部 AI プロンプトへ原文を渡さない |
| URL・ファイル名 | リンク・共有 URL | fetch、unfurl、アクセス解析 | CDN/WAF、Referer、アクセスログ | 患者識別子を URL に載せない。自動 fetch/unfurl を停止 |
| 再取込・派生データ | バックアップ復元・インポート | 再索引、要約、再試行、export | キャッシュ、バックアップ、成果物、Git | 派生物も同じ機密区分。復元後も未確認状態から開始 |

## 3. 検知 → 隔離 → マスキング → 人の確認

1. **入口で隔離を先行**: 未確認入力は承認済みローカル領域でのみ受ける。原文を Cloudflare、Slack、外部 STT/LLM、共有 Graph、テレメトリへ通さない。受入場所・権限が未整備なら受入拒否。クラウド経由してからマスキングする構成は封じ込めにならない。
2. **ローカル検知**: 氏名、患者番号、住所、連絡先、日付、希少疾患、施設・担当者・受診時刻の組合せなどを検査する。OCR/STT 失敗、暗号化添付、判定器停止、タイムアウト、未知形式も「疑い」。陰性でも自動公開しない。
3. **隔離の維持**: 原文と派生物に同じ区分・ランダムな追跡 ID を付与し、通常検索、ベクトル化、学習、SSOT 昇格、エージェントのツール入力から外す。キュー/DLQ・再試行でも出口を再検査。隔離は通常ワークスペースと別権限・別保存先とする。
4. **マスキング案作成**: 人名だけでなく準識別子・画像・ファイル名・文書属性も除去または一般化。対応表が必要なら原文側だけに保管し、外部へ出す候補に含めない。仮名化を匿名化とみなさず、復元可能な ID や内容は患者情報として扱う。
5. **人による最終確認**: 医療機関が指定した確認者が原文と候補を閉域で比較し、用途・送信先・必要最小限性・再識別リスクを確認。保守担当の判断だけで解除しない。ダミー例は「架空患者 TEST-PATIENT-001、架空施設 TEST-CLINIC」。実在データ由来の改変例は使わない。
6. **送信先単位の解除**: 確認者・時刻・候補の版・用途・送信先・有効期限を本文なしで記録する。人の確認と送信承認は別条件。契約・出口許可がない場合は確認済みでも送らない。版変更、送信先変更、期限切れは再確認。許可済み候補のみ出口ゲートを通し、原文の暗黙の再添付を禁止する。

自動検知には偽陰性・偽陽性があり、病歴や組合せによる再識別を完全には検出できない。**既定は隔離を維持し、疑わしきは人の確認待ち**。マスキング済みというラベルだけで公開可能と判断しない。

既に外部へ混入した場合は、その経路の取得・再試行・通知を停止する設計とする。患者情報を含まない追跡 ID だけで責任者へ報告し、流出先・派生先を確認する。遠隔削除や通知は承認を受けた別作業とする。

## 4. ログ・一時保存・バックアップ・鍵・保守アクセス

すべて設計上の上限案。運用責任者・医療機関による承認前に有効化しない。法的保全が必要な例外は理由・期限・権限を記録して通常データと分離する。削除手順は将来の承認済み運用として記述し、今回実行しない。

Cloudflare を患者情報経路の候補から外すことはしないが、本番可に変えるには、少なくとも入口で外部へ渡さない構成、製品単位の処理/保存/鍵/ログの所在地と再委託の確認、契約上の保持/削除の合意、医療機関側の承認、事故対応・出口遮断・復元時再混入防止の検証が必要。DLS の契約だけで全製品を承認したことにしない。

作業時の一時資料 `/workspace/cf-cutover-design.md`（2026-10-15、リポジトリ内の恒久参照ではない）は外部 DNS と Pages 等の配信切替の検討資料として読んだ。患者データ処理・契約の保証には使わず、内容や顧客設定を本リポジトリへ転載しない。参照候補の顧客資料分離 story は今回所在を確認できず、根拠として採用しない。

## 7. 検証計画（実装後、合成ダミーのみ）

本 PR は文書のみ。以下は未実施の検証手順であり、staging 合格・本番安全性を報告するものではない。

1. 外部接続を禁止したローカル/隔離 staging を用意し、STT/LLM/Slack は送信記録だけを持つ stub にする。患者情報を受ける Cloudflare の実経路は使わない。
2. 各入力経路へ合成ダミー、準識別子の組合せ、隠しシート、画像メタデータ、OCR 不能ファイルを用意する。原文が検索・埋め込み・会話・ログに現れず、外部への送信が0件であることを確認する。
3. 判定器障害、通信断、再試行、DLQ、期限超過、人の却下で解除されないことを確認。承認済み候補も別送信先・版変更では停止することを確認する。
4. 合成データ専用環境で、保持満了・権限失効・バックアップ復元・削除済み ID の再取込を模擬する。実削除操作は別承認後に限る。
5. 権限の異なる確認者/保守/一般利用者で原文閲覧境界を検証する。第三者への原文持出しなしで、本文を含まない判定結果と trace のみ証跡にする。
6. 合格条件: 未承認原文送信0件、原文の通常保存0件、疑い/障害/復元時の隔離100%、期限/版/送信先不一致の解除0件。検知精度は別途測定し、この合格を匿名化保証とはみなさない。
