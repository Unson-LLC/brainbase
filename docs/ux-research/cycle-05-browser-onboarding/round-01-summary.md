# Round 1: OSS導入導線のブラウザ評価

## 結論

32人の独立したペルソナが、固定した4タスクを実ブラウザで評価した。失敗判定と安全上の重大ゲート違反は0件だった。一方、22人が中断・再開または複数ページへの情報分散を具体的な摩擦として記録した。

採用する改善は、既存の詳しい説明を削らず、初回利用者向けに「開始、MCP登録、Judgment Host登録、成功確認、復旧」を一枚で追える再開可能な最短導線を追加することとする。

## 固定タスク

1. トップからBrainbaseの価値を一文で説明する。
2. 前提条件、最初の依頼文、開始コマンドを見つける。
3. Codex MCPからJudgment Hostへ進む順序と成功確認を見つける。
4. 既存設定を上書きせず、失敗や中断から復旧する。

## 観測結果

| 観測 | 人数 | 判断 |
|---|---:|---|
| 固定4タスクを可視Playwright Chromiumで評価 | 32/32 | 評価完了 |
| `failed` または `fail` の判定 | 0/32 | 重大な到達不能なし |
| 中断・再開・複数ページ分散を明示 | 22/32 | 共通摩擦として採用 |
| 既存設定の上書き防止を確認 | 31/32 | 既存契約は維持 |
| 404リソースを観測 | 22/32 | `/favicon.ico` の404を再現し修正対象に採用 |

価値文、開始プロンプト、`onboard:start`、dry-run、自動マージをしない境界、MCPを先に確認してからJudgment Hostへ進む順序は、既存文書を横断すれば確認できた。主な問題は情報不足ではなく、現在地と次の一手を利用者自身が再構成する必要があることだった。

## 証拠境界

- ペルソナ評価は合成評価だが、各評価は実際のVitePress UIを可視ブラウザで操作した。
- 32件のJSONと32件のスクリーンショットを個別に保存した。
- 実在利用者の観察、VoiceOver、物理端末、実MCP登録、実Hook登録は `not_collected` であり、成功へ丸めない。
- `gpt-5.6-luna` を指定したが、実行時のモデル識別情報は取得できないため、モデルbindingは `not_collected` とする。
- ペルソナ属性は `rotation-manifest.json` を正本とし、個別JSON内の表記ゆれは集計の正本にしない。

## 次の変更

1. トップとサイドバーに「最短で試す」を追加する。
2. 一枚のチェックリストに、開始、MCP、Judgment Host、成功確認、再開方法を統合する。
3. 設定ファイルのバックアップと元へ戻す判断を明記する。
4. faviconを明示し、再現した404を解消する。
5. 同じ固定タスクを、16 anchors、16 rotatingのRound 2で再評価する。
